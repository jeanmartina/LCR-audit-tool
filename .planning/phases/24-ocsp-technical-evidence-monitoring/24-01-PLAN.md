# Phase 24 Plan 24-01: OCSP Storage, Types, and Validator Foundation

**Created:** 2026-05-04  
**Status:** Ready for execution

## Objective

Create the OCSP evidence data model and focused validator that later plans will use for real request generation, responder checks, worker integration, and proof closure.

## Scope

### In Scope

- OCSP technical event/evidence TypeScript types.
- Runtime schema for `ocsp_check_events` and `ocsp_response_evidence`.
- Runtime-store helpers for recording and listing OCSP evidence/events.
- Initial `scripts/validate-ocsp-monitoring.js` wired into `scripts/validate-all.js`.

### Out of Scope

- Installing `pkijs`/`asn1js`.
- Generating OCSP requests.
- Fetching responder URLs.
- Worker scheduling.

## Threat Model

<threat_model>
T-24-01: OCSP evidence can grow without bounds if raw response storage is added without byte metadata and explicit helper boundaries. Mitigation: storage schema includes request/response sizes, hashes, raw `bytea` fields, and later plans must enforce byte limits before calling storage helpers.

T-24-02: Semantic OCSP status values can leak into monitoring health and create false compliance claims. Mitigation: OCSP event types use technical statuses only and validator forbids `good`, `revoked`, and `unknown` as event health states.
</threat_model>
